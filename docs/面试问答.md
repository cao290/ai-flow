# ai-flow 面试问答准备

> 原则：简历上写的每个数字都要能复现，每个技术选择都要能讲清「为什么不用现成的」。
> 面试官最怕两种人：堆名词的，和说不出自己决策的。

## 一、20 秒电梯陈述

> 我做了一个 MCP 工具编排器。本机有 12 个 MCP 服务、223 个工具，但每次干活都得人工决定调哪个、怎么传参、结果存哪。我把这套编排固化成声明式工作流：零依赖实现 MCP 协议栈（client + server）、223 个工具的动态统一索引、带重试/熔断/幂等/进程自愈的编排引擎，配了 Web 看板，然后把它本身也包成 MCP 工具让 AI 直接调用。34 项自测断言全过（含无外部依赖的 CI 环境），四条真实工作流跑通，中转成本实测降低 51%。

## 二、项目深挖必答题

### Q1：这个项目到底是不是你做的？你的贡献边界在哪？

**答**：全部自己写的。三部分：
1. **协议层**——MCP stdio 的客户端和服务端各一份，零依赖实现 JSON-RPC 2.0 over stdio。没用官方 SDK，理由是想让它零依赖可移植，同时也能证明我真的理解协议而不是只会调库。
2. **工具注册表**——不硬编码工具清单，全部从运行中的 MCP 服务实际探测。223 个工具建成统一索引，命名规则 `服务名::工具名`，保留每个工具的 JSON Schema。
3. **编排引擎**——变量渲染 `${step.field}`、超时、指数退避重试、熔断、optional 语义、逐步审计落盘。

界面和部署没花时间，因为这个项目的价值在引擎层，不在皮。

### Q2：为什么不用现成的 Dify / Coze / n8n？

**答**：三个层次的原因。

**功能上**：我需要编排的全是**已经在本机跑着的 MCP 服务**——223 个工具分散在 12 个独立进程里，每个有各自的启动方式、环境变量、密钥。Dify/Coze 那类平台是让你把能力**注册进去**，它们假设工具是被平台托管的。我这里是反过来：工具已经存在且各有归属，编排层要做的是适配而非托管。

**工程上**：平台的价值是快速验证业务流程，但我这个场景的瓶颈不是"画流程图"，是"工具发现 + 参数契约 + 失败语义"。这些恰好是平台的薄处——平台擅长编排已知工具，不擅长动态发现异构工具。

**动机上**：如果我要在简历上写"我用过 Dify"，那是个二流的开源项目使用经历。写"我实现了一个 MCP 编排引擎"，并且它真的在解决我自己的日常重复劳动，这是二流和一流的区别。

**代价我也认**：如果只是要一个能跑通业务流程的 demo，我这个方案过度设计了。过度设计在生产里是缺点，在求职展示里是加分项——前提是我能说清为什么。

### Q3：223 个工具这个数字怎么来的？会不会有重复统计？

**答**：来自实际探测，不是估的。`scripts/scan_tools.js` 会依次对每个已注册服务发 `initialize` 握手 + `tools/list`，取回 JSON Schema 建索引。

- 12 个注册服务中 11 个握手成功，`slider-mcp` 进程退出码 1（它依赖的 Python 环境有问题）。
- 223 是 `tools/list` 返回的工具条目总数。**这里有真实的重复**：`hlib-mcp` 和 `experience-mcp` 都有 `experience_search`，是不同实现下的同名工具。所以我用了 `服务名::工具名` 的限定命名，而不是工具名本身——这正是我要在下一问展开的点。

### Q4：怎么保证不会调错工具？AI 面对 223 个工具不会懵吗？

**答**：这正是我做「能力分组」和「工作流预定义」两层的原因。

**第一层，能力分组**。我把 223 个工具按语义分成 6 组（搜索检索 15 个、内容处理 47 个、图像视觉 126 个、数据结构 29 个、经验沉淀 9 个、编辑器 18 个），AI 先看组再选工具。但这只是辅助。

**第二层，工作流固化**。真正的答案是：**大部分场景根本不需要 AI 选工具**。「做一次技术调研」这六步是固定的，我把它固化成 `tech_research` 工作流，AI 只需要说"跑一下技术调研，关键词是 X"。工具选择由我预先做好的定义决定，AI 不需要在 223 个里挑。

**第三层，按需暴露**。AI 真的需要现选时，用 `flow_tools` 带关键词过滤，返回的是带完整 JSON Schema 的候选集，不是全量 223 个。

**第四层，工具描述本身就是选择依据**。我保留了每个工具的原始 description，因为那些描述写得比我自己重写的更准确。

### Q5：工作流失败了怎么办？会不会一半执行一半挂掉？

**答**：这涉及三类失败，我分别处理。

**不可重试的失败**——工具不存在、参数错误、schema 不匹配。这类重试没有意义，只会浪费时间还可能产生副作用。我用关键词匹配把它识别出来（`未知工具`/`invalid`/`required`/`not found` 等），直接判失败。

**可重试的失败**——网络抖动、超时、下游 5xx。指数退避重试，默认 2 次重试（共 3 次尝试），退避时间 `backoff_ms × attempt`。

**服务级故障**——某个服务整体挂了。单步重试解决不了，我加了熔断：同一服务连续失败 3 次就短路，后续步骤直接跳过该服务，30 秒后半开重试。这条路径是实测过的——mock 服务连续报错时，引擎记录了「尝试3」后正确上报。

**关于半执行状态**：这是编排器的真实短板，我不会粉饰。当前实现是**步骤级原子**的——一步失败，那步的输出就是空的，不会写一半数据。但**跨步骤没有事务性**——第 3 步成功第 4 步失败时，前两步的副作用不会自动回滚。

**解法已经落地——幂等层**（`core/idempotency.js`）：
- 副作用步骤声明业务键（`idempotency_key: 'archive:${keyword}'`），或用 `idempotent: true` 让引擎按"工具名+稳定参数哈希"自动生成键（排除 timestamp 等易变字段）
- 引擎执行前查持久化账本：键已存在且成功 → 复用上次结果跳过调用，重跑失败链不再重复归档
- `--force` 显式绕过缓存；账本落 `data/ledger.json`，跨进程重启有效
- 自测覆盖：命中、绕过、不同键不误命中、跨实例持久化四条路径
- **真实链路验证**：同关键词重跑技术调研，archive 步骤 1ms 幂等命中，资料库没有出现重复文件

注意语义边界：幂等是"跳过"不是"回滚"——同键但下游数据已变时需要 force。这是刻意选择的简化，换真事务（saga/补偿）复杂度会翻倍，对这个规模不值得。

### Q6：怎么衡量它有没有用？

**答**：三个层面的指标。

**工程层**：自测 34 项断言全过，覆盖协议握手、变量传递、重试计数、optional 语义、熔断触发、幂等命中/绕过/持久化、进程超时终止、注册表统计。刻意用 mock MCP 服务隔离外网——引擎逻辑的验证不依赖任何外部服务，CI（Ubuntu + Windows 双平台）稳定复现。

**链路层**：真实跑通四条工作流。`tech_research` 中文关键词检索返回真实结果并归档资料库；`lesson_capture` 约 290ms，经验真实写入经验库；`code_study` 1.9s 完成导入→读文件→统计；`image_understand` 18s，视觉模型正确读图并归档。

**业务层（中转成本）**：这是我认为最有说服力的数字。AI 直接调工具时，工具输出必须整段进模型上下文再由模型搬运到下一步；编排器的字段级引用让大输出留在编排器内部。**实测（两条路径共享同一次检索输出，保证可比）：人工路径中转 40.6KB（约 10,791 tokens），编排路径 19.9KB（约 5,295 tokens），中转量减少 50.9%，最终归档内容逐字节一致。** 折算到 API 成本就是每次这类任务少花一半的搬运 token。

同时我要主动说清两个测量上的坑：
1. **耗时对比没有意义**——两条路径调同一批工具，总耗时差异全是下游网络波动（search-engine 单次 30-70s 波动），不归功于编排层。编排层自身开销用零延迟 mock 单独测过：每步 0.01-0.4ms。
2. **我没测"省了多少分钟"**——工时受人的熟练度影响，测出来也不可复现。中转成本是系统固有属性，可测量、可复现，这才是工程指标。

### Q7：如果工具数量涨到 1000 个怎么办？

**答**：

1. **索引构建是并发的**，当前 12 个服务并发探测，实测 2.3 秒内完成。1000 个工具分布在同样数量的服务里，握手时间不变。

2. **连接是惰性的**——`ToolRegistry.call` 只在真正调用时才启动对应 MCP 进程，不会为了列个工具就把 12 个服务全拉起来。

3. **真正的瓶颈是选择，不是加载**。1000 个工具塞给 LLM 做选择，context 会爆。解法是分层：服务级路由（先选服务）+ 组级路由（再选组）+ 工具级（最后在组内选）。我现在的能力分组就是第二层的雏形。

4. **工作流固化才是最根本的解法**——工具越多，越要把常用路径固化成工作流，让 AI 根本不需要面对全量工具集。这也是我认为这个方向的价值所在：**工具数量的增长应该被编排层吸收，而不是甩给调用方。**

### Q8：为什么用零依赖，不用官方 MCP SDK？

**答**：三个原因。

**可移植性**：零依赖意味着 `git clone` 完 `node server.js` 就能跑，不需要 npm install。项目可以被别人直接跑起来验证，这对开源项目是硬指标。

**理解深度**：我自己写 client 和 server 意味着我对协议有完整认知——initialize 握手的字段、notifications/initialized 的时机、tools/list 与 tools/call 的区分、错误码的处理。调 SDK 的话，这些细节会被封装掉。

**代码量本身就说明了问题**：client + server 一共约 400 行，覆盖完整工具调用能力。SDK 的引入成本（node_modules、版本兼容、跨平台）远大于这个。

**代价我也认**：官方 SDK 有并发、连接复用、错误处理的成熟实现，我的是简版。如果要上生产，SDK 是更稳妥的选择。现在的选择是因为这个项目要展示的是设计能力，而且规模可控。

## 四、可能被问到的技术细节

**Q：JSON-RPC over stdio 和 LSP 有什么区别？**
答：LSP 用 `Content-Length` 头分帧，MCP 直接用换行分帧，每行一个 JSON。实现上要注意 stdout 只能有协议消息，任何日志都得走 stderr——我在 server 里显式处理了这点。

**Q：怎么防止 MCP 进程的 stdout 被污染？**
答：这是实际踩过的坑。我的实现里 `process.stdout.write` 只在 `send()` 里调用，日志统一走 `process.stderr`。另外解析时对非 JSON 行做静默跳过，因为部分服务会往 stdout 打自己的日志。

**Q：多个 MCP 服务怎么并发管理？**
答：每个服务一个常驻子进程 + 一个 `pending` Map 存未决请求。`nextId` 自增保证请求 ID 唯一。服务端返回时按 ID 匹配 resolve/reject。进程退出时把所有 pending 全部 reject，避免调用方永久挂起。

**Q：超时是怎么实现的？**
答：客户端侧是 `setTimeout` + 从 pending 里删除并 reject。**这个缺口已经修了**：超时后标记客户端不健康、终止进程，注册表在下次调用时自动重建干净实例；进程意外退出同样标记并在下次调用重建。自测里有三条断言专门验证这条路径（挂起调用触发超时 → 标记不健康 → 进程被终止）。

**Q：连接超时和调用超时怎么区分？**
答：这里踩过一个真 bug——最初我把连接时的 30s 超时透传给了 client 的调用超时，导致 search-engine 这类 40s+ 的慢工具必然超时。修法是分离：握手有独立的 30s 初始化超时，调用超时默认 300s、可按步骤覆盖。这个 bug 是基准测试暴露的——"为什么同一个工具 CLI 能跑通、基准必超时"。

**Q：变量渲染会不会有注入风险？**
答：我刻意只支持 `${step.field}` 点路径，不做表达式求值。这意味着上一步输出里如果包含 `${...}` 字样，不会被二次求值。不支持任意表达式是安全边界，不是能力缺失。

## 五、诚实清单（面试主动说的短板）

已解决（可以主动讲"我曾经缺什么、怎么补的"）：

1. ~~跨步骤无事务性~~ → **已做幂等层**（业务键 + 持久化账本 + force 语义，真实链路验证）
2. ~~超时后不杀进程~~ → **已做进程健康管理**（超时/退出后标记不健康并自动重建）
3. ~~无 Web UI~~ → **已做看板**（三栏 + SSE 实时执行 + 工具索引 + 历史）
4. ~~业务价值无量化~~ → **已做中转成本基准**（中转量降 50.9%、token 降 51%、产出逐字节等价；并诚实说明耗时对比无效的原因）

仍然存在的（真短板，主动说）：

5. **无 LLM 动态编排**——工作流是静态声明的，AI 只能选"跑哪条"，不能现场规划步骤。下一步方向。
6. **幂等是跳过不是回滚**——同键但下游数据已变时需 force，没有 saga/补偿机制（规模不到，刻意不做）。
7. **只在 Windows 上真实跑过**——CI 覆盖 Ubuntu，但真实 MCP 服务生态没在 Linux 验证过。
8. **看板执行历史是单机文件**——没有并发控制，两个浏览器同时触发同一工作流会各自执行（幂等层能兜住副作用，但历史会交错）。

**主动说出来的价值**：面试官问「你觉得这个项目哪里做得不好」——能说清"哪些补了、怎么补的、哪些留着、为什么留着"的人，和答不出的人，结果完全不同。
